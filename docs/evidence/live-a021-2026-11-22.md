## Findings

### 1. `policies` Degraded: the Kyverno reports controller could not read the Karpenter CRDs

The ValidatingPolicy `karpenter-config-from-git` matches `karpenter.sh/v1
nodepools` and `karpenter.k8s.aws/v1 ec2nodeclasses`. Its status said
`Policy is not ready for reporting, missing permissions: get, list, watch`
on both, so `ready: false`, and Argo CD 3.6 showed the `policies`
Application Degraded. The other six policies, which match core resources,
were ready. **Admission still worked**: a server-side dry-run change to the
NodePool by a human IAM user was denied with the policy's message.

**Fixed** in #81 (merged 10:29): `reportsController.rbac.clusterRole.extraResources`
in `gitops/apps/kyverno.yaml`, which the chart turns into the aggregated
ClusterRole `kyverno:reports-controller:additional` with get, list and
watch only. It ships in the next tag; the session ran v2.4.0 without it.
Not yet proven live. Follow-up: a CI check that the reports controller can
read every non-core resource a ValidatingPolicy matches (today CI renders
the Kyverno chart without the app's values).

### 2. First request after Ready: 8.35 s, objective under 8 s

The 16-token warmup probe of operator v0.17.0 ran before Ready, and the
first client request still took 8.35 s, against 5.7 to 6.6 s for the next
ones: a residual of about 2.5 s, close to the ~2 s residual seen on v0.11.2
(5.84 s against 3.81 s). In CI on v0.34.0 (Intel Xeon 6975P, 4 CPUs) the
residual was 0.1 s (2.76 s against 2.65 s). The difference between CI and
EKS is not explained yet. Hypotheses to test in CI, not live: the request
shape (the probe sends 32 tokens, the warmup 16; prompt lengths differ),
and the CPU budget (1 core with its hyperthread on m7i-flex.large, against
4 CPUs on the runner).

### 3. Steady state on v0.34.0 is about 50 % slower than v0.11.2 on the same nodes

p50 5.86 s against 3.81 s, with the same probe, the same instance type, the
same pod resources and the same `warmupStrategy: Eager` (`--enforce-eager`)
as on 2026-11-21. The only change in the serving path is the vLLM release
(v0.11.2 to v0.34.0).

- **Refuted in the session:** the OpenMP binding. With the default
  (`auto`), vLLM v0.34.0 reserves 1 CPU and binds the engine to core 1 only.
  With `nobind` the p50 moved from 5.86 s to 5.72 s, within noise. Probable
  reason: the 2 vCPUs of an m7i-flex.large are the two hyperthreads of one
  physical core.
- **Open:** eager mode on v0.34.0. The start-up log shows that with eager
  mode torch.compile is off and the IR ops run the `native` implementations.
  Default mode compiles; on one core that adds minutes to Ready, which is
  why it was not tried in the session.
- **Next step:** a CI study, same request as the probe, on 1 and 2 CPUs:
  v0.11.2 eager, v0.34.0 eager, v0.34.0 default, with the CPU model next to
  every number. The live comparison is not repeated until CI explains the
  gap.

Until then, claims about v0.34.0 on EKS state the numbers of this session
as they are: steady p50 5.9 s on 1 m7i-flex core in eager mode.
