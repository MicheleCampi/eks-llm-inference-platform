# Experiment evidence: Envoy 503 "connection termination" against the vLLM idle timeout, on kind (2026-11-25)

Protocol and hypotheses: [`experiments/prefix-routing/KEEPALIVE.md`](../../experiments/prefix-routing/KEEPALIVE.md),
written before the run. Workflow: `.github/workflows/keepalive-503.yml`.
Cost: 0 (GitHub-hosted runners, no AWS resources).

Run [45596624007](https://github.com/MicheleCampi/eks-llm-inference-platform/actions/runs/45596624007),
commit 765b752. Same set-up as the scorer-parity run
([`scorer-parity-2026-11-25.md`](scorer-parity-2026-11-25.md)): EPP built
from llm-d-router main at `32a075e2`, chart `llm-d-router-standalone` from
the same checkout (Envoy as a sidecar of the EPP pod), vLLM CPU v0.34.0,
2 replicas, Qwen2.5-0.5B-Instruct. Both arms (legacy, ea), 3 repetitions
each, order alternated, 160 requests per arm at concurrency 4.

The run was repeated on the next commit of the pull request
([45606788302](https://github.com/MicheleCampi/eks-llm-inference-platform/actions/runs/45606788302),
commit e4fbffd, same workflow and set-up), so the 600 s condition has two
replications. The 1 s condition has one: in four attempts across the two
runs, three produced no data because the two vLLM replicas did not finish
engine start-up (warm-up about 135 s, then no `Application startup
complete`) before the 10-minute startup probe limit, twice in a row, and no
request was sent. The probes got `connection refused`, so the HTTP server
was not listening and the keep-alive setting was not yet in use. The
attempt that started (run 45596624007, attempt 2) is the one reported. The
runners' CPU models were not logged; the workflow now records them.

## Hypotheses

| # | Hypothesis | Result |
|---|---|---|
| K1 | 1 s: more than 1 failure in 960, every failure with flag `UC` | **not met**: 1 failure in 960. It carries flag `UC`. |
| K2 | 600 s: 0 failures in 960 | **met**, in both runs (0 in 1920) |

As written before the run, with K1 not met the idle-connection race is not
shown by this run.

## Reading

- What the run shows: the failure is Envoy's `UC` flag, "upstream connection
  termination", on the connection from Envoy to the vLLM pod the EPP chose
  (`upstream` is a model-server address). The model server's side of that
  connection closed before any response bytes. The EPP had already done its
  part; the failure happens after routing.
- The rate does not separate the conditions: 1 in 1280 at the vLLM default
  of 5 s (scorer-parity run, both arms), 1 in 960 at 1 s, 0 in 1920 at 600 s,
  and 1 in 2880 at 5 s on llm-d-router v1.0.0 with the legacy scorers
  (prefix-routing run, 2026-11-23). The failures appear under both scorer
  configurations.
- A limit of the design, found after the run: at concurrency 4 with
  back-to-back requests, a pooled connection is rarely idle for 1 s, so the
  1 s condition did not produce many more idle closes than 5 s. A test of the
  race needs idle gaps between requests (for example pauses of 1 to 5 s);
  this run does not have them.

## Consequence for llm-d-router #2059

The failure in the scorer-parity run is a connection reset between Envoy and
vLLM, recorded with flag `UC` after the EPP had picked the pod, and seen with
the legacy scorers as well. It does not bear on the scorer comparison.
Whether it is the idle-connection race stays open.
