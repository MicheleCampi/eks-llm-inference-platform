## Result

On one m7i-flex.large Spot node (**Intel Xeon Platinum 8488C**, Sapphire
Rapids, AMX and AVX-512, 1 core / 2 threads), same pod settings (eager mode,
request 1 CPU, 6 GiB, `VLLM_CPU_KVCACHE_SPACE=1`, `--max-model-len 2048
--dtype bfloat16`), same probe (`{"prompt":"Kubernetes is","max_tokens":32}`
every 2 s plus latency):

| Run | vLLM release | Window | Requests | Failed | p50 | p95 | max |
|---|---|---|---|---|---|---|---|
| A1 | v0.11.2 | 14:21:58 to 14:31:00 | 95 | 0 | **3.694 s** | 3.781 s | 4.237 s |
| B | v0.34.0 | 14:35:17 to 14:45:19 | 82 | 0 | **5.372 s** | 5.566 s | 5.643 s |
| A2 | v0.11.2 | 14:48:16 to 14:56:20+ | 116 | 0 | **3.705 s** | 3.804 s | 3.849 s |

**B/A1 = 1.45, A2/A1 = 1.003.** By the rule written before the session
(B/A ≥ 1.3 with A1 and A2 within 10 %), **the regression is real on this
CPU**: vLLM CPU v0.34.0 is about 45 % slower at steady state than v0.11.2 for
this model and request shape on Sapphire Rapids. The node did not drift (A2
matches A1 within 0.3 %). p50 and p95 exclude the first request of each
window.

How this fits what was known:

- A-021 measured p50 5.86 s on v0.34.0 and A-020 3.81 s on v0.11.2, on
  different m7i-flex nodes and days. A-022 reproduces both numbers on one node
  (5.37 s and 3.69/3.71 s): the gap was the release, not the node or the day.
- The CI study (operator runs 45018253568, 45020445163) found at most ~10 %
  between the releases on **Intel Xeon 6975P (Granite Rapids)**. The
  regression therefore depends on the CPU generation: present on Sapphire
  Rapids (8488C), absent or small on Granite Rapids.
- First request after Ready on v0.34.0: **5.34 s** (14:35:17), the same as
  its steady state. On this node the operator's 16-token warmup leaves
  nothing to warm: A-021 finding 2 (8.35 s) did not recur. A2 (v0.11.2) first
  request: 3.61 s. A1's first request was not measured (operator SSH dropped
  before the probe started).

Claims stated from now on: "vLLM CPU v0.34.0, p50 5.37 s on m7i-flex.large
(Xeon 8488C), 1.45 x v0.11.2 on the same node", never a single number without
the release and the CPU.

## Findings

### 1. vLLM CPU v0.34.0 steady-state regression on Sapphire Rapids (A-021 finding 3, confirmed)

Same node, same pod, same probe: v0.34.0 p50 5.37 s, v0.11.2 3.69 s and
3.71 s. Next steps:

- An upstream issue to vLLM (CPU backend) with this data: model and
  revision, both image digests, the CPU (`/proc/cpuinfo` model and flags,
  `lscpu`), pod settings and the two CI runs on Granite Rapids where the gap
  is ≤ 10 %. Before opening it: search for an existing issue, and reproduce
  outside Kubernetes on an m7i(-flex) instance or any Sapphire Rapids host if
  one is available at no cost (the CI runners do not offer that CPU).
- The platform stays on v0.34.0: v0.11.2 has 80 fixable CRITICAL CVEs,
  including vLLM CVE-2026-22778 and CVE-2026-48746. The number is stated as
  measured, with release and CPU.
- `tests/ab/model-v0.11.2.yaml` and its image-scan baseline line (expiry
  2026-11-29) are removed in the same PR as this evidence: the image is not
  deployable outside the A/B. The manifest stays in Git history (commit
  ca37c1e) for the upstream repro.

### 2. First request after Ready on v0.34.0 is warm on this node

5.34 s against a steady p50 of 5.37 s: the operator v0.17.0 warmup (16-token
completion before Ready) is enough here. A-021's 8.35 s came 12 minutes after
Ready on a different node; it is not reproduced.

### 3. Operator session dropped mid-run (process)

The SSH session dropped while waiting for A1. No data was lost except A1's
first request after Ready. Commands from then on carried the node name
literally instead of a shell variable, so a reconnect needed nothing.
