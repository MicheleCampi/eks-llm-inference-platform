# A-023 evidence: vLLM CPU steady-state slowdown bisected to v0.19.1 -> v0.20.x on Sapphire Rapids (2026-11-22)

Follow-up of [live A-022](live-a022-2026-11-22.md) finding 1. On one Xeon
8488C EKS node, vLLM CPU v0.34.0 was 1.45 times slower at steady state than
v0.11.2. This session finds the release where the slowdown starts. It runs on
the same CPU, outside Kubernetes, in plain Docker.

- **Budget:** A-023, with a ceiling of 1,00 EUR and at most 3 h. Michele approved it at 16:35Z.
- **Machine:** one EC2 `m7i-flex.large` On-Demand in eu-west-1a (instance `i-017d245ed1516ead9`), in the default VPC with no inbound port. Its CPU is an **Intel Xeon Platinum 8488C** (Sapphire Rapids), 2 vCPUs, with `amx_bf16` and `avx512f`.
  - `m7i.large` was planned, but the account's Free Tier plan refuses it (`InvalidParameterCombination`). `m7i-flex.large` is the same type as the A-022 node.
- **Software:** Amazon Linux 2023 `ami-04060762724eee84a`, Docker. Scripts are in `vllm-coldstart-operator` `hack/sapphire-bisect/` at commit `35445e9` (study branch):
  - `bisect.sh` drives the bisect;
  - `images.txt` lists the 24 releases, one per minor from v0.11.2 to v0.34.0, each by digest;
  - `user-data.sh` runs it all and powers the instance off;
  - the measurement is `steady-study/study.sh`.
- **Per run:** a fresh eager server (`--enforce-eager --max-model-len 2048 --dtype bfloat16`) with `VLLM_CPU_KVCACHE_SPACE=1`, `--cpuset-cpus 0,1` and 6 GiB, serving Qwen2.5-0.5B-Instruct at revision `7ae5576`. It gets the operator v0.17.0 warmup (16 tokens), then 40 serial requests of the game day probe (`"Kubernetes is"`, 32 tokens). Each release is run twice; the reported p50 is the median of the two runs. p50 and p95 exclude the first probe request.
- **Search rule, written before the session:** stop if v0.34.0/v0.11.2 < 1.3. Otherwise binary search with the midpoint of the two p50s as threshold, then v0.11.2 again as the drift check.
- **Billable window:** launch at 17:50:12Z, instance powered itself off at 18:54:40Z (about 64 min). No instance or volume tagged `Session=A-023` left (0 and 0, checked by Michele at 19:16Z).
- **Roles:** Michele was the operator and ran every command. The AI agent wrote the scripts, the commands and this evidence.

| Release | Rep 1 p50 / p95 | Rep 2 p50 / p95 | p50 (median) | Ready s | Verdict |
|---|---|---|---|---|---|
| v0.11.2 | 3.79 / 3.83 | 3.81 / 4.56 | **3.80** | 30, 40 | fast |
| v0.16.0 | 3.86 / 3.91 | 3.95 / 3.99 | **3.905** | 30, 30 | fast |
| v0.19.1 | 3.78 / 3.84 | 3.79 / 3.83 | **3.785** | 31, 30 | fast |
| v0.20.2 | 5.70 / 5.80 | 5.75 / 5.85 | **5.725** | 70, 70 | slow |
| v0.22.1 | 5.80 / 6.03 | 5.77 / 5.89 | **5.785** | 75, 75 | slow |
| v0.34.0 | 5.20 / 5.36 | 5.21 / 6.93 | **5.205** | 45, 45 | slow |
| v0.11.2 (control) | 3.77 / 3.82 | 3.79 / 3.86 | **3.78** | 30, 35 | drift −0.5 % |

All 560 measured requests answered HTTP 200 (14 runs × 40).

- **The step is between v0.19.1 and v0.20.2** (the 0.20 minor: v0.20.0, v0.20.1 or v0.20.2). It is +51 % at steady state: 3.785 s to 5.725 s.
- **v0.34.0 is partly better than v0.20-v0.22:** 5.21 s against 5.73-5.79 s, but still 1.37 times v0.11.2. A-022 measured 1.45 on EKS. The difference is the setup: Docker against a pod, and a fresh instance against a node that had been up for 20 minutes.
- **Time to Ready also jumps at the same release:** 30 s to 70 s. A start-up change in v0.20 (for example kernel selection or warmup at load) could be connected. That is a hypothesis, not tested here.
- **The machine did not drift:** the control run is within 0.5 % of the first.
- **Same distribution channel on both sides of the step:** v0.19.1 and v0.20.2 both come from Docker Hub `vllm/vllm-openai-cpu`, so the step is not an artefact of the image source. v0.11.2 is from ECR Public, but it sits in the fast group with v0.16.0 and v0.19.1, which are on Docker Hub.

## What changed inside the image (free, after the session)

Inspected by digest on a GitHub runner (operator run 45060069713, workflow
`sapphire-bisect-inspect.yml`, study branch):

| | v0.19.1 (fast) | v0.20.0 | v0.20.2 (slow) |
|---|---|---|---|
| torch | **2.10.0+cpu** | **2.11.0+cpu** | 2.11.0+cpu |
| oneDNN (MKL-DNN, bundled in torch) | **v3.7.1** | **v3.10.2** | v3.10.2 |
| MKL | 2024.2 | 2024.2 | 2024.2 |
| intel-openmp | 2024.2.1 | 2024.2.1 | 2024.2.1 |
| triton | 3.6.0 | 3.6.0 | 3.7.0 |
| transformers | 5.5.4 | 5.6.2 | 5.8.0 |
| `LD_PRELOAD` | tcmalloc + libiomp5 | same | same |

The image environment, the OpenMP runtime and MKL are the same on both sides
of the step. **The PyTorch upgrade 2.10 → 2.11 is new in v0.20.0, and with
it oneDNN 3.7.1 → 3.10.2.** oneDNN holds the bf16 AMX matmul kernels a
Sapphire Rapids decode step uses. That makes it the first suspect,
**not yet proven**: vLLM's own CPU code changed in 0.20 too. The test that
separates them does not need vLLM. A torch-only bf16 linear layer timed at
decode shapes (M = 1-8, the Qwen2.5-0.5B projection sizes) on torch 2.10 and
2.11, on Sapphire Rapids, against Granite Rapids as control.

## Process notes

- The Free Tier plan restricts instance types. `m7i-flex.large` is allowed; `m7i.large` is not.
- The user-data plus `instance-initiated-shutdown-behavior=terminate` worked:
  - no SSH or inbound port was needed;
  - the instance stopped itself 106 min before its hard stop;
  - the operator's SSH dropped during the session and nothing was lost.
- The first monitor command did not save the console lines to a file. Console output stayed readable 20 minutes after termination. A monitor for the next session saves them to a file on each round.
